# 编码规则（第一性原理）

> `code-agent` 主职责参考。动笔写代码前必须按本章完成定位与决策；写的时候对齐现有实现，而不是发明第二套风格。

---

## 一、第一性原理：实施前先回答四个问题

编码前用现有代码库回答，写不出来就继续搜，禁止凭空开写：

| # | 问题 | 目的 |
|---|------|------|
| 1 | **最小成果是什么？** | 本任务验收通过后，系统多了什么可观察能力？只为实现该能力改代码 |
| 2 | **落点在哪里？** | 现有哪一层 / 哪个模块已经承担同类职责？优先扩展，避免平行新树 |
| 3 | **什么可复用 / 该封装？** | 已有工具、模式、错误类型能否直接用？重复逻辑是否已值得抽出？ |
| 4 | **怎么证明做对了？** | 用项目现有测试方式覆盖 Happy Path + 边界 + 异常；没有测试基建时至少有可执行验证步骤 |

输出（可简短，但必须有）：
```
落点：<目录/模块 + 理由>
复用：<现有符号/文件，或「无，新建理由」>
封装：<抽出 / 不抽出 + 理由>
验证：<测试命令或手工步骤>
不做：<本任务明确不碰的点>
```

---

## 二、落点定位（写在哪里）

按优先级探测，命中即停，不要跳过：

1. 任务/计划里已写的「目录/模块结构」「涉及文件」
2. `docs/architecture.md` / `CLAUDE.md` / `AGENTS.md` 中的目录与分层约定
3. 仓库内**同类功能**的现有实现（同名领域、同层模块）
4. 包管理与构建入口（`package.json` / `pyproject.toml` / `go.mod` 等）暗示的源码根
5. lint / CI 配置中的路径约定

**禁止：**
- 无理由新建与现有分层平行的目录（如已有 `services/` 却另起 `logic/`）
- 把业务逻辑塞进无关的 util / 入口文件「图方便」
- 在未确认调用方的情况下改动高 fan-in 公共模块的对外签名

**不确定时：** 先 Read 1–2 个最相近模块，再决定；仍不定则向用户确认落点，不赌。

## 三、复用与封装

### 3.1 复用优先

动手前搜索：
- 同名/近义函数、类型、错误码、常量
- 项目统一的请求/响应包装、日志、配置读取
- 已有测试 helper / mock 工厂

能扩展现有函数完成验收 → **不要**再写一个几乎一样的。

### 3.2 何时封装

满足任一条件再抽：
- 同一逻辑将出现 ≥2 处，或已有复制粘贴迹象
- 逻辑有独立验收价值（纯函数、策略、状态转换）
- 抽出来能显著降低主路径分支噪音

**不要封装：**
- 只调用一次的样板胶水
- 为「看起来干净」而过度抽象（过早接口 / 过深间接层）
- 跨层泄漏的「万能 util」

### 3.3 边界

封装后的符号应落在**已有边界**内（同 package / 同 layer），并沿用现有导出方式；不要为单个任务引入新的「公共层」。

---

## 四、编码前对齐清单（强制）

写第一行业务代码前完成：

- [ ] Read 至少 1 个同类现有实现（目录、命名、错误处理、日志）
- [ ] Read 至少 1 个同类测试（目录、命名、断言、mock 方式）——若项目有测试
- [ ] 扫一眼相关 lint / formatter / typecheck 配置
- [ ] 确认不引入项目未使用的新依赖（除非任务明确要求）
- [ ] 若任务含「不做」字段，逐条记住

新领域（缓存、队列、鉴权等首次引入）→ 可补充搜索官方文档推荐模式，**用项目风格重写**，禁止整段粘贴异风代码。

---

## 五、风格与结构（跟仓不跟臆想）

| 维度 | 规则 |
|------|------|
| 命名 | 文件名、符号名与邻近模块一致（kebab / camel / snake 以现仓为准） |
| 目录 | 新文件放在第二节定位的落点；测试文件跟现有测试树走 |
| 错误处理 | 复用项目错误类型 / 返回约定；不混用另一套 error 风格 |
| 日志 | 复用现有 logger 与级别习惯 |
| 类型 | 优先扩展已有类型；共享结构放在项目惯用位置 |
| 注释 | 公共 API、复杂分支、非显而易见决策、magic number 必须注释；自解释代码不堆注释 |
| 改动面 | 只改验收所需；不做顺手重构、不扩 scope |

---

## 六、测试与验证

**核心逻辑**（有业务分支 / 转换 / 校验 / API 处理）必须有测试，至少三类：

| 类型 | 要求 |
|------|------|
| Happy Path | 正常输入 → 预期输出 |
| 边界值 | 空、极值、上限附近 |
| 异常路径 | 非法输入 → 预期错误 |

框架与目录：跟现有测试基建；没有则用语言标准框架，并放在与现仓一致的位置。

非核心改动（纯配置、文案）可不强求单测，但须有任务级验证方式（命令或 2–3 步手工检查）。

---

## 七、实施中与实施后

### 实施中
- 发现落点判断错误 → 停下重做第一节四问，再改，不要硬写
- 必须碰共享文件 → 最小化 diff，并在报告中说明
- 并行任务（若有）→ 不写入未授权文件

### 实施后自检
- [ ] 验收标准逐条可判定通过
- [ ] 落点与第一节声明一致（有偏差须说明原因）
- [ ] 风格与邻近模块一致
- [ ] 核心逻辑测试或约定验证已完成
- [ ] 若来自计划任务：已回写计划 checkbox（任务 / 验收 / 已完成测试项）

---

## 八、与计划任务字段的关系

若任务来自详细计划，按以下映射使用可选字段（有则遵守，无则用本章自行推断）：

| 计划字段 | 编码时用法 |
|----------|------------|
| 目录/模块结构 | 落点约束（第二节） |
| 数据结构 / 接口契约 | 形状约束，不另起一套 |
| 逻辑概要 | 关键分支按伪代码实现，禁止样板 CRUD 扩写 |
| 涉及文件 | 优先在此范围内改；越界须说明 |
| 验证方式 | 最低验证义务 |
| 不做 | 硬边界，不可「顺手做了」 |
