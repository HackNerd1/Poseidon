# 计划生成支持（附职责）

> `code-agent` 的**附职责**参考。主职责是代码实施；仅当 `plan`（或其他编排方）需要构造 planning sub-agent prompt / 验收计划文档时加载本文件。
>
> 计划文档结构模板仍属于 `plan` skill（`overall-plan-template.md` / `plan-template.md`）。本文件只提供 sub-agent Prompt 与计划文档验收清单。

---

## 一、何时使用

| 调用场景 | 加载章节 |
|----------|----------|
| 生成总体计划 | 二.1 + 三.1 |
| 生成详细计划 | 二.2 + 三.1 |
| 仅验收计划文档 | 三.1 |

Agent 类型：默认 `general-purpose`。与 `plan` 步骤对应：总体计划 → plan Step 4；详细计划 → plan Step 5。

## 二、Planning Sub-Agent Prompt 模板

### 2.1 总体计划生成

```
## 任务：生成总体计划 — <功能名称>

### 输入材料
- 需求文档：<path-to-requirement-doc>
- 澄清记录：<path-to-clarification-doc>
- 计划模板：`plugins/dev-tools/skills/plan/references/overall-plan-template.md`

### 任务要求
根据需求文档和澄清记录，按 overall-plan-template.md 的结构生成总体计划文档。

关键原则：
1. **垂直切片**：Phase 1 为最简端到端流程（Tracer Bullet），覆盖所有技术层但只实现 Happy Path
2. **阶段数量**：
   - 小型需求（<5 任务）→ 1 阶段
   - 中型需求（5-15 任务）→ 2-3 阶段
   - 大型需求（15+ 任务）→ 3-5 阶段
3. **依赖关系**：明确标注阶段间的依赖，允许并行的阶段标注为可并行
4. **第一性原理**：先写最小用户价值 / 系统价值、必要成立条件、高风险假设，再做阶段划分
5. **默认极简**：只保留阶段划分、依赖、放行信息；不要把执行状态、实验记录、过程性结论混入正文
6. **进度间接展示**：阶段任务、完成标准、里程碑统一使用 todo list，不单独写显式进度百分比、状态汇总或进度条

### 架构约束
<如果有项目约束文档，列出关键约束；否则写"基于通用最佳实践">

### 输出要求
1. 生成总体计划文档，写入 `docs/requirements/<feature-slug>-overall-plan.md`（或调用方指定的存储路径）
2. 列出每个阶段的宏观任务（todo list 形式）
3. 标注阶段间的依赖关系
4. 如存在高风险假设，加入最小可行性验证阶段或宏观任务；否则不要为了完整性强行加入
5. 如流程图 / 时序图不能显著降低理解成本，则省略

### 报告格式
完成后报告：
1. 计划文档路径
2. 阶段数量和各阶段任务数
3. 关键风险点
4. 建议的下一阶段（Phase 1）详细计划生成策略
```

### 2.2 详细计划生成

```
## 任务：生成详细计划 — <功能名称> — Phase <N>: <阶段名称>

### 输入材料
- 需求文档：<path-to-requirement-doc>
- 总体计划：<path-to-overall-plan>（如果有）
- 澄清记录：<path-to-clarification-doc>
- 计划模板：`plugins/dev-tools/skills/plan/references/plan-template.md`

### 任务要求
根据输入材料和 plan-template.md 的结构，为 Phase <N> 生成详细实施计划。

关键原则：
1. **垂直切片**：每个任务是一个完整的功能片段，而非水平技术层
2. **任务粒度**：默认单阶段 3-5 个任务；只有复杂阶段才放宽到 6-7 个
3. **依赖清晰**：任务间依赖形成有向无环图，标注可并行任务
4. **可验证**：每个任务有明确的、二值的验收标准
5. **第一性原理**：先写“本阶段的最小可交付成果是什么”，再拆任务
6. **禁止机械拆分**：不要把同一条最小交付链路拆成 `skeleton / implementation / wiring / docs`
7. **默认极简**：只写未来工作、未完成项、依赖、放行条件；不要混入当前进展、样本统计、临时结论
8. **todo 统一**：任务、验收标准、测试场景、人工验证步骤统一使用 todo list；进度通过勾选状态间接体现
9. **任务级可选项按触发表展开**：必填仅任务 / 描述 / 验收标准；目录/模块结构、数据结构、接口契约、逻辑概要、涉及文件、验证方式、不做等可选字段严格按 plan-template.md 触发表写入，不为完整性强行填满

### 架构约束
<如果项目有约束文档，列出关键约束>

### 输出要求
1. 生成详细计划文档，写入 `docs/requirements/<feature-slug>-detailed-plan-p<n>.md`（或调用方指定路径）
2. 任务 ID 格式：`<SLUG>-P<phase>-<seq>`（如 `LOGIN-P1-01`）
3. 包含依赖关系图（文本或 Mermaid）
4. 如阶段需要明确 gate，可保留 1 个 Final Gate；否则不要为了模板完整性添加检查点
5. 任务级可选字段按触发表按需添加（参见 plan-template.md「任务级可选字段触发表」）
6. 简单任务可只保留任务 / 描述 / 验收标准 / 依赖；复杂任务至少补齐命中触发条件的 1-2 个可选字段

### 报告格式
完成后报告：
1. 计划文档路径
2. 任务清单（ID + 标题 + 规模 + 依赖）
3. 可并行执行的任务组
4. 建议的派发策略（串行/并行/分批）
```

## 三、计划文档验收

### 3.1 Planning Sub-Agent 验收

- [ ] 计划文档已写入指定路径
- [ ] 文档结构符合对应模板（overall-plan-template / plan-template）
- [ ] 阶段/任务划分符合垂直切片原则
- [ ] 先定义了最小用户价值 / 系统价值或最小可交付成果，再进行阶段/任务拆分
- [ ] 依赖关系明确，无循环依赖
- [ ] 任务没有被机械拆成 `skeleton / implementation / wiring / docs`
- [ ] 任务、验收标准、测试场景、人工验证步骤使用 todo list
- [ ] 任务级可选字段仅在命中触发表时出现；无触发却填满视为滥用，有触发却完全缺失视为该写未写
- [ ] 简单任务未被迫填满可选项；复杂任务至少补齐命中触发条件的 1-2 个可选字段
- [ ] 检查点等其余可选章节仅在确有必要时出现
- [ ] 计划正文没有混入执行日志、当前进展、样本统计、临时结论
- [ ] 架构约束已纳入考量

### 3.2 不通过处理

| 问题 | 处理方式 |
|------|---------|
| 结构不符合模板 | 要求按模板重写缺失章节 |
| 机械拆分 / 过度拆分 | 合并同一条最小交付链路后重交 |
| 可选字段滥用或该写未写 | 按触发表增删后重交 |
| 混入执行过程信息 | 删除过程性内容后重交 |
